## 3.0.3.4 — 2026-10-03

### Features
- **Driver deliveries no longer wait for Order Done** — when the driver app sends a delivery, Tracker saves the proof (with the GPS point and delivery order) and replies straight away (about 0.1–0.5 s instead of 5–15 s or more). Order Done, the Woo "Completed" update and the emails (proof of delivery, note to the office) then run in the background on the server, as the driver (logs show the driver's login). The proof's status goes *Pending* → *Completed* (or *Order Done failed*, or *already done*). Work cut off by an app restart is picked up at the next start, delivery upload or visit to **System → Driver App**. No new app or APK needed: the app already shows the server's reply as is.
- **System → Driver App → Deliveries Waiting for Order Done** (administrators) — every delivery from the app whose order is still not done in Tracker: still being completed, left for the office ("run Done" off), failed (with the reason), or with items to follow (link to the order). **Complete Now** runs Order Done for it again and shows the result; the proof of delivery is not emailed twice. Older deliveries saved before "run Done" was on show up here too, so the office can finish them in one click. Each retry is logged (Delivery log) with who asked.
- A Woo order that could not be marked Completed does not stop Order Done; the reason is kept in the proof's status message and the Woo log.

### Go-live notes
- Upload `bin/` and `Tools/DriverApp.aspx`. No schema change and no `Web.config` change other than `Version`.
- After the first start open **System → Driver App** and check **Deliveries Waiting for Order Done**: older driver deliveries whose order was never done are listed; use **Complete Now** for those that really were delivered, or finish them from the order as before.

## 3.0.3.3 — 2026-10-03

### Features
- **Route order by road driving times** — each driver's suggested order (Delivery Sheet, driver app, Delivery order) is now worked out on real road driving times from HeiGIT (openrouteservice matrix, the same HeiGIT key as the address lookups) instead of straight lines, so Table Mountain, the M3 / N2 and one-way streets count. Up to 13 stops the quickest order is found exactly; above that the nearest-stop route is improved by reversing stretches and moving one to three stops until nothing gets quicker. The driver's own order and the order they usually deliver in still come first, as before. On dev: Sibusiso's 30 Sep stops 99 → 95 minutes of driving, 1 Oct 122 → 118.
  - Each pair of points is fetched once (one call for the whole day's set of a driver, at most 59 points) and kept 180 days in `RoadLegTbl`, so regular clients cost nothing after the first time. At most 450 calls a day (HeiGIT's free plan allows 500).
  - **System Preferences → GPS & Drivers → Route Order → Road driving times** (on by default) shows today's calls and how many legs are kept. Without the HeiGIT key, when it is off, or when HeiGIT can't be reached, the route uses straight lines as before; after an error no call is made for 15 minutes (2 after the per-minute limit, until tomorrow after the daily limit). Each call and each pause is logged (Delivery / System log).
  - Expected arrival times are not changed (still straight line × 1.3 at the average speed, as in the driver app).
- **Driver deliveries run Order Done** — **System → Driver App → "Complete the order in Tracker (run Done) when the driver sends a delivery"** was off, so a delivery from the app only saved the proof: no cup count, usage, predictions, recurring order update or order done. The update turns it on once (later changes on that page are kept). Deliveries with items still to follow are still left for the office.
- **Order Done marks the Woo order Completed** — when Tracker finishes an order that came from Woo (Order Done page, Delivery Sheet Done or the driver app), the Woo order is set to Completed, so Woo sends the customer its "order complete" email. Courier and dispatch orders (waybill entered, "order dispatch" message, or delivered by a dispatch person such as Courier / Pargo) stay open with the waybill note, as before. Orders already completed, cancelled or refunded in Woo are left alone. Setting: **Tools → WooCommerce Mapping → General → Mark the Woo order Completed on Order Done** (on by default). The result shows in the Order Done message and the Woo log.

## 3.0.3.2 — 2026-10-02

### Features
- **Depot: Set on map** — **System Preferences → GPS & Drivers → Set on map** opens a map popup (`Tools/DepotLocation.aspx`, administrators) with the depot pin: drag it or click the map, type or paste co-ordinates (or a Google Maps link), or search an address, then *Save depot point*. Road / Satellite with Azure Maps. Typing co-ordinates in *Depot address* and pressing *Save* also sets the point. Editing the address text alone no longer clears the point (it changes only with Set on map, typed co-ordinates or Look up depot). Changes go to the System log.
- **Driver app updates itself (Android)** — `npm run apk` now writes `Downloads/QuaffeeDriver.json` (version) next to the APK, and the app's lookups carry it (`settings.app`). When Tracker has a newer version, the app shows **Update** on the delivery list and under **More**: it asks for a download link (`GET /api/v1/app/download`, valid 30 minutes, signed with the site's machine key) and opens it in the phone's browser (`GET /api/v1/app/apk?t=…`, no Tracker sign-in needed in the browser), then the driver taps Install. **Tools → Driver App** shows the version. Works from 0.5.1 on; older apps are updated by downloading once from the Driver App page.
- **Delivery Sheet: drag to order a driver's stops** — open stops for our own drivers (not couriers or collections), today or later, have a ⠇ handle. Drag stops within a driver's group, then **Save order** (or **Cancel**) in the yellow bar. The order goes to the same route plan the driver app uses (`DeliveryRouteTbl`, `SetBy` = "user (office)"); stops already delivered keep their place. The driver's own order takes precedence: if the driver set their order in the app, saving asks first. The hint and a line per driver (who set the order and when, with **use the suggested order** to drop the plan) sit at the bottom of the sheet, with a link to **Delivery order**. The app shows the driver *"The office (user) set your order at …. You can still change it."* until they change it. Logged in the delivery log.
- **Tools → Delivery order is a live board** — per driver (own drivers first, then couriers / collections), the day's stops in route order with a status that changes as deliveries happen, as in the driver app: *Delivered HH:mm · how · received by*, *Not delivered HH:mm · reason*, *Collected by the client HH:mm*, *Done in Tracker*, **Next · about HH:mm** (highlighted) and *about HH:mm* for the rest. A summary line per driver (On route / All done / Not left the depot yet, "X of N done", last stop about HH:mm, when the phone was last seen, who set the order) and a progress bar. Opens on today and refreshes every minute; ◀ ▶, **Today**, a date and a driver filter for other days (past days show stops not captured in the app). The order the drivers really delivered in (visits) is still listed below.
- **Delivered and expected times** — the driver app shows *delivered HH:mm*, a Next marker and "about HH:mm" for the rest on its list, and Delivery order shows the same. The Delivery Sheet no longer shows route numbers or times (it stays a clean sheet), so the User Information option *Show route order and arrival times on the Delivery Sheet* is gone. Expected times start only once the driver is more than 300 m from the depot or has made a delivery, and chain from the latest of the last delivery and the last position: straight line × 1.3 at the *Average speed*, plus the *Minutes per stop* (System Preferences → GPS & Drivers). Stops with no GPS point use the average leg and show "~" / "roughly".
- **"Does the GPS point need updating?" on delivery** — when signing a delivery the driver app says how the phone's position compares with the client's point: matches, will set / replace / move it (looked-up or driver points), the hand-placed pin is kept (and flagged when far off), the phone is too rough, or the phone is far from the client. **Contact Details → Proof of Delivery** has a *GPS point* column with the same check (orange when it needs looking at). The mobile sheet now carries each stop's point (`gps`), `noGpsLearning` and `routeNote`; the lookups carry `settings.route` (speed, minutes per stop, depot, 300 m).

- **"Collected by the client" / "Dropped off by the supplier"** — new delivery outcomes for orders booked to a driver that the client collects (or a supplier drops off). **Lookups → Delivery Outcomes** has a new **Not at client** tick (on for both new options). A proof captured with such an option keeps the phone's position (where it was signed) but it never moves or sets the client's GPS point, never counts towards the driver's learned delivery order, and is not used as "where the driver was" for expected times. The driver app says so when the option is chosen, and its "far from the client" warning suggests these options. **Contact Details → Proof of Delivery** shows "not at the client … position not used", and **Driver tracking** shows the option (e.g. "Collected by the client") instead of "done". The server decides from the option text, so phones on older app versions are covered too. Schema pack `SQLCommands-DriverGps-04.xml` (runs at start-up): `MobileDeliveryOptionsTbl.NotAtClient`, `MobileDeliveryProofTbl.NotAtClient` and the two options.

- **Administration → Manage Users** — new **Type** column: *Staff* with the roles, or *Contact Portal* with a link to the contact. New **Last login** column: the latest of signing in to Tracker, to the Contact Portal and using the driver app ("· portal" / "· driver app"; "never (created …)"), in orange when older than 2 years. **Show** (All logins / Staff / Contact Portal / Not used for 2 years), a search on user name, email or company, sortable headers and 25 rows per page. A bar shows how many logins have not been used for 2 years, with **Show them** and **Delete N unused logins** (asks first; administrators and your own login are never included — delete those one by one from Manage). Deleting a user (here or **Delete User** on User Information) now also removes their preferences and Contact Portal link and revokes their driver app sign-ins; you can no longer delete the login you are signed in with. On User Information the option is now called **May see driver tracking** (lets a non-administrator open Deliveries → Driver tracking; administrators always can).

- **Terms on the driver app signature** — as on the old printed delivery sheet, the person signing now accepts our terms: above the signature the app shows the statement (*"I acknowledge receipt of the items listed … subject to Quaffee's standard terms and conditions available at quaffee.co.za"*) with a tick box and **Read the terms** (opens the terms page). A delivery with a signature can't be sent until the box is ticked and the signer's name is filled in under *Received by* (so the POD never says "no name given" next to a signature). The proof stores whether it was ticked and the exact wording shown (`TermsAccepted`, `TermsText`). **Tools → Driver App** has the wording and the terms link (empty = the defaults); the link must be a full web address.
- **Proof of delivery PDF** — the client is now emailed a **proof of delivery (PDF)** instead of a short note with the signature: order and PO number, delivered to (name, address), when and how, received by, driver, what was handed over (qty and delivered), anything still to follow, the terms with the tick (and who ticked it) and the link, and the signature. The **Email the client** setting on **Tools → Driver App** is now *Email the client the proof of delivery*. What was handed over is stored with the proof (`HandedOver`) so the PDF shows what the driver confirmed then, even if the order changes later.
- **Send the POD from Tracker** — **Contact Details → Proof of Delivery** has a **POD** column: **PDF** opens the proof of delivery, **Email** sends it to the client (or to the address typed above the list), with the orders address copied, and then shows *emailed d MMM HH:mm to …*. A *Terms* column shows *accepted* / *not ticked*. Walk-in clients (ZZName) get a *Walk-in* column and the email goes to the `[#email#]` in the order notes. The PDF is also at `Handlers/ProofOfDelivery.ashx?id=…` (staff see any proof; Contact Portal logins only their own). Schema pack `SQLCommands-DriverGps-05.xml` (runs at start-up): the proof's terms, handed-over and POD-sent columns and the Driver App terms settings.
- **Proof of Delivery on the Contact Portal** — clients can now open and download their own proof of delivery PDF in My Quaffee. **My Orders** has a *Proof of Delivery* column with **View** (opens the PDF in a new tab) and **Download** for delivered orders (the latest proof per order). **Order Details** has a *Proof of Delivery* section listing every delivered proof for the order (when, received by, View / Download). Not-delivered reports are not shown. A portal login asking for a proof that isn't its own gets "Proof of delivery not found." (tested with another contact's proof and a made-up number). Admins see the same in **View as** on the portal.

### Fixes
- **"Cannot have multiple items selected in a DropDownList" when adding the first item to a new order** — when the delivery person was changed from the contact's preferred one before adding the first item, the order was saved with the preferred person anyway and the page then crashed redrawing the list (the order and line were saved). The chosen delivery person is now used (the preference only fills in when the list is on n/a), and selecting a delivery person or contact clears the old selection first.
- **Walk-in (ZZName) stops in the driver app** — the stop showed "ZZName________"; it now shows the walk-in's name (the text before the `:` in the order notes) as the client and the address / goods after the `:` as the stop's notes, without the `[#…#]` tags. The office Delivery Sheet, driver notes to the office and the POD use the same rules (`SundryNotes`).
- **Walk-in email address** — the address was taken from the first `[#…#]` tag, so a payment tag such as `[#41405: Yoco]` before `[#name@mail#]` gave no or a wrong address. Only a tag holding an email address counts now.
- **Monthly recurring orders delivered early came round again** — a "day of month" line (e.g. the 1st) took the next date as that day in the month after the last delivery, so coffee delivered on 25 Sep for 1 Oct was due again on 1 Oct and a second order went out. A delivery now counts for the target day nearest to it (early ones for the coming month, late ones for the month just past, a tie for the past one) and the next date is the one after that: 25 Sep → next 1 Nov; 7 Sep → next 1 Oct as before. Same rule in the checkup, Order Done and the recurring order screens (`DateCalculator.NextMonthlyCycleAfter`).

## 3.0.3.1 — 2026-10-01

Includes the GPS delivery work, driver tracking and Quaffee Driver 0.5.0 on top of the order flags release prepared on 2026-09-29 (never deployed separately).

### Features
- **Contact Details → Proof of Delivery tab** — every delivery the driver app recorded for the contact: order, when, outcome, how it was delivered, who received it, signature, items not handed over, driver note, driver and a map link to where it was signed. Shown only when the contact has proofs.
- **Driver app "how it was delivered" list** — the list is configurable on **Lookups → Delivery Outcomes** (formerly *Driver Options*, now linked from **Tools → Driver App**). New option **Collected**, for when the driver collects something (no name asked by default).
- **Lookups → People → Delivery Type** replaces the *Dispatch* tick box: *Does deliveries* (our own driver), *Courier (waybill)* (Order Done asks for the courier company and waybill number, as Dispatch did; Contact Details shows the Courier list), *Collect (shop)* (customer collects from the shop) or *None*. First run: SQ, WM and MX → Does deliveries, Cllct → Collect, dispatch people → Courier. The column header tooltip explains each type.
- **Customer GPS locations** (step 1 of the GPS delivery plan) — contacts whose *Delivery By* person is a *Deliver* person get a GPS point looked up once from their address (HeiGIT openrouteservice; only the address, postcode and "South Africa" are sent). It is looked up again only when the address changes. It is looked up when the contact is saved, on the first order for one of our drivers, or in bulk on **Tools → Customer Locations**. Rough matches (suburb or postcode only) are marked *Needs checking*.
  - The contact's **area** is added to the lookup as the suburb when the address doesn't already name it (text in brackets and words like "surrounds" are dropped; "A / B" uses the first name). If that gives only a rough match, the plain address is tried as well and the better result is kept. The map popup search is prefilled the same way.
  - Automatic lookups only accept matches within 150 km of the depot (when the depot point is set), treat `;` in an address as a new line, and ignore province/country-level matches (the postcode point is used instead). This stops matches like "Claremont" → Clermont (KZN).
  - Addresses are tidied before the lookup: "c/o …", company names ending in (Pty) Ltd, shop / unit / flat / floor numbers and estate / complex / building names (when a street line is present) are left out. Up to three versions are tried (tidied with the area suburb, tidied, as typed) until one matches the address itself. The popup search is tidied the same way.
  - **Contact Details:** the GPS line shows the co-ordinates with a small status badge (filled tick = checked, outlined tick = looked up, "?" = needs checking); the geohash, where the point came from and the match are in the tooltip. The map popup is larger with no scroll bars, has a button panel (Save this pin, Look up again, Close), can be dragged by its title bar, and closes after *Save this pin*. Closing with a moved pin that is not saved asks: *Save and close*, *Close without saving* or *Keep editing*. The status badge sits next to the *GPS* caption.
  - **Tools → Customer Locations:** new **Look up rough ones again** button for the *Needs checking* list (pins placed by hand are never touched; a rough point that still can't be found is removed so the stop falls back to its area).
- **Route order uses GPS, not areas** — on the delivery sheet and in the driver app, each driver's stops for the day are put in driving order from the depot using their geohash points: always the nearest stop not visited yet, then crossings in the route are removed. Areas no longer decide the order. A contact without a point yet is placed at its area's busiest geohash cell; stops with neither (no point and no located contact in the area) go last in the old area order (Lookups → Delivery Days). Delivered stops keep their place so the numbers don't shift during the day.
  - **Learns the driver's own order** — every delivery sent from the driver app (delivered or not) records which stop of the day it was for that driver and contact (several orders at one stop count once; a delivery sent late is slotted in by its time). The suggested order then starts from where each driver usually delivers a contact (the last 10 visits before that day, the route's driver first), blended with the GPS route: one visit counts half, four visits 80%, ten visits 91%. Contacts never visited keep their GPS place, then the area order. A day never learns from itself, so stop numbers don't shift during the day; days with fewer than 3 stops are not learnt from. Proofs already received are counted once when the update first runs. Each visit is logged in the Delivery log ("Delivery order: driver 3 … was stop 2 of 8").
  - **Tools → Delivery order** (linked from **Tools → Driver App**) — the order deliveries were really made per day and driver: stop number, time (and a later visit the same day), contact, area, and where the stop sits in today's suggestion.
  - **Driver app:** stops are numbered 1, 2, 3… in route order in one *Route* list (*Everyone* has a heading per driver); the area is shown under each name. Phones need the new APK (older APKs still get the new order, but with area headings).
  - **Contact Details:** new *GPS* line under Packaging with **Check / change**: a map where the pin can be confirmed, dragged or looked up again. A saved pin is marked *Checked*.
- **System Preferences → GPS & Drivers** — new tab: geocoding key (stored in the database, never shown again), daily and per-minute lookup limits with today's count, map tiles (OpenStreetMap), depot address with *Look up depot*, driver tracking (on/off, interval, weekdays only, work hours, how long positions are kept) and arrival-time settings (average speed, minutes per stop, marker colour thresholds). Tracking and arrival times drive the Driver tracking page.
- **User Information** — two per-user options, both off by default: *Show route order and arrival times on the Delivery Sheet* and *Show driver tracking* (opens Deliveries → Driver tracking to non-administrators).
- **Azure Maps address lookups** — **System Preferences → GPS & Drivers → Lookup service** chooses HeiGIT (OpenStreetMap, free) or **Azure Maps** (much better at South African street addresses; 5,000 free lookups a month, then pay per 1,000). Each service has its own key (stored in the database, never shown again, with *Remove the saved key*) and its own daily count. Azure Maps results are limited to 150 km of the depot like HeiGIT's.
  - Azure Maps points are kept at most **180 days** (Microsoft's terms for results stored outside Azure). From 30 days before that date they are looked up again on the next order, contact save or batch, and a point past its date that could not be refreshed is removed (once a day). The GPS tooltip and popup show where each point came from and how long it is kept.
- **Driver app: position with each proof** — the app now sends where the phone was (and how accurate that was) with every delivered / not-delivered report. It starts listening when the capture screen opens and never holds up the driver if there is no fix or location is refused. Android asks for location permission once. Needs the new APK.
- **Tracker learns customer points from deliveries** — when a *Delivered* proof arrives with a phone fix of ±75 m or better:
  - no point yet, or a looked-up / postcode point → the driver's position becomes the point (*from the driver's phone*, no expiry, so the Azure 180-day rule no longer applies to it);
  - a later visit (6 hours or more apart) within 60 m of the driver point → the point is averaged and marked **Checked**; further away → the point moves to the new position;
  - pins placed by hand are never moved; if two visits in a row are more than 150 m away, the pin is flagged *Needs checking* (a later agreeing visit clears it);
  - the sundry contact is skipped. Each decision is written to the Customers log, and the Delivery log now records the GPS and accuracy of each proof.
- **No GPS for courier / collect contacts** — a contact whose own *Delivery By* person is a *Courier* (e.g. Pargo, Cour) or *Collect* person is never looked up automatically (not on contact save, not when an order for one of our drivers is captured, not in the open-orders batch), and phone positions from deliveries to them are not kept (logged). *Look up again* in the popup still works on request.
- **Azure Maps map** — **System Preferences → GPS & Drivers → Map** chooses OpenStreetMap or **Azure Maps** for the GPS popup. Azure Maps has a *Road / Satellite* switch (satellite with street names). The tiles come through Tracker (`Handlers/MapTile.ashx`, signed-in users only), so the Azure key never reaches the browser; at most 15,000 tiles a day (1,000 transactions), with today's count next to the setting. Without a saved key, or if Azure refuses the tiles, the popup shows OpenStreetMap. Map changes and tile failures (at most once a minute) go to the System log.
- **Look up depot** — the result now shows at the top of the GPS tab and next to the button (it used to appear at the bottom of the page).
- **Contact Details:** the "?" badge (needs checking) now lines up with the *GPS* caption like the tick does.
- **Deliveries & Areas** — new top menu **Deliveries** and page `Tools/Deliveries.aspx` (also a card on the home page) with everything for deliveries in one place: Delivery Sheet, Delivery order, Driver App, Move delivery date, Customer Locations, GPS & driver settings, and the Lookups tabs Areas, Delivery Days, People, Couriers, Delivery Outcomes and Packaging (each opens on its tab), plus Holiday closures. Driver App moved here from the System menu.
- **Driver sets the route order** — in the driver app (*Mine*), **Change order** shows the day's stops with ▲ ▼ buttons; **Save order** sends it to Tracker (`POST /api/v1/delivery/route`). That order then comes before the learned and GPS order, in the app and on the office Delivery Sheet, until the driver taps **Suggested order**. With no signal it is kept on the phone and sent when there is signal. Stored in the new `DeliveryRouteTbl`; each change is in the Delivery log. **Tools → Delivery order** has a *Driver's plan* column next to the order really delivered.
- **Packaging colours in the driver app** — the packaging's background colour from Tracker (Lookups → Packaging) is shown behind the pack name on the list and on the stop, as on the delivery sheet.
- **No WhatsApp for landlines** — **Tools → Driver App → Landline numbers start with** (default `021`; e.g. `021, 011, 087`). The app shows only *Call* for those numbers and offers WhatsApp on the cell instead. Numbers are matched the local way, so +27 21… and 0027 21… count as 021. Changes are in the System log.

### Features
- **Mobile REST API for a delivery driver app** — JSON API at `/api/v1` (ASP.NET Web API 2, inside the Tracker site) for an Android / iPhone app. Drivers sign in with their Tracker login, which must be linked to a person in Lookups → People (Security Username). Administrators can sign in without being linked.
  - **Sign-in:** `POST auth/login` returns a long-lived device token (90 days, `MobileApi.TokenDays`), sent as `Authorization: Bearer <token>`. Only a hash of the token is stored. Signing in again on the same device replaces its old token; `POST auth/logout` revokes it, and administrators can list and revoke devices (`GET devices`, `POST devices/{id}/revoke`). `GET auth/me` returns the user and person.
  - **Delivery sheet offline:** `GET delivery/dates` and `GET delivery/sheet?date=&person=me|all|id` (the driver's own deliveries by default; they can open another driver's or everyone's to help out, and the request log notes it) return each stop with the contact person's name (for ZZName orders, the name from the order notes), phone, cell, address, area, notes, PO, items and any proof already captured, in delivery order.
  - **Proof of delivery, captured offline:** `POST delivery/sync` takes a batch of deliveries (received-by name, signature image, note, time, location, or Not Delivered). Each carries a phone-generated `clientRef`, so retrying a sync never records it twice. By default the proof is stored and the office completes the order; System → Driver App can run Order Done straight away instead. `GET delivery/proofs` and `GET delivery/proofs/{id}/signature` show what was captured.
  - **Repairs:** `GET repairs` (open only, by contact, or changed since a time), `GET repairs/{id}`, `POST repairs` (create; `clientRef` makes offline creates safe to retry) and `PUT repairs/{id}` (send only the fields that change). Saves follow Repair Detail: the related order is kept in step and the contact is emailed on a status change.
  - **Lookups and contacts:** `GET lookups` (repair statuses, faults, machine types, conditions, people, driver options) and `GET contacts?q=` / `GET contacts/{id}`.
  - **Driver options:** the choices the app offers when capturing a delivery ("Left at reception", "Handed to an assistant", "No signature obtained"; "Nobody there", "Rejected / refused" …) are edited in Lookups → Driver Options. "Needs name" makes the driver enter who received it or get a signature. The chosen option is stored with the proof (`Reason`).
  - **Items not handed over:** the driver ticks off what was handed over; anything short or to follow is stored with the proof (`MissingItems`), and such a delivery is never auto-completed, so the office can sort out the rest.
  - **Repairs on the sheet:** each stop lists its item lines with order line ids, marks repair (Service) lines, which are not handed over, and includes the repairs linked to the order (job card, machine, serial, fault, status).
  - **Data efficient:** replies are gzip-compressed (the sheet is about 7 KB, 2 KB on the wire), nulls are left out, and the sheet, dates, repairs and lookups carry an ETag, so the app gets a 304 with no body when nothing has changed. Phones may also gzip what they send.
  - **Security:** HTTPS is required except on the server itself (`MobileApi.RequireHttps`), and cross-origin calls are only accepted from the app origins in `MobileApi.CorsOrigins`. Tables are created automatically on first use (`SQLCommands-MobileApi-01.xml`).
  - **Request log:** every call is recorded (time, user, call, result, time taken, bytes each way, IP address, and a short note such as "Sign-in failed for 'x'" or "3 deliveries: 3 saved"). Only these facts are kept, never what was sent, so passwords, tokens and signatures are not logged. Kept for 30 days (`MobileApi.LogDays`; 0 turns it off). Administrators can read it with `GET log`.

ZZName orders use the address in the order notes. When Order Done also runs, its "delivered" email is skipped so the client gets one email.

- **Mobile API hardening:**
  - Too many failed sign-ins from one IP address (any usernames) pause sign-ins from there for 15 minutes with a 429 (`MobileApi.LoginFailuresPerIp`, default 10), on top of the normal lockout after 5 wrong passwords.
  - A phone not used for 30 days must sign in again (`MobileApi.TokenIdleDays`).

  - Each phone may make 120 calls a minute (`MobileApi.RequestsPerMinute`); more get a 429 with Retry-After.
  - Signatures and the proof list are administrators only, and signatures are never cached.
  - Every API reply is marked no-store (unless it carries an ETag), nosniff, no framing and no referrer; HTTPS replies send Strict-Transport-Security.

  - The ASP.NET version header is no longer sent.
  - The API Tester's Settings & security tab shows the new settings.

- **Editable waybills after Order Done** — Order Detail shows waybill as display-only with a pencil; popup to correct number/courier, optional customer notify email (`Order.WaybillUpdated*`), and Woo customer note when linked.
- **Tracking welcome email** — New contacts (Contact Details insert and Woo create) that are tracking-enabled get a thank-you / checkup intro from Messages.resx with a Disable Client link.
- **Disable Client choices** — Clear options for reminders-only vs disable account entirely, with short explanations and matching success copy from Messages.resx.
- **Send Reminder on Contact Details** — Manual one-off checkup reminder (no order created); uses Messages.resx wording, updates reminder count/log after a successful send.
- **Duplicate waybill guard** — Order Done and waybill edit block reuse of the same tracking number + courier; warning names the previous customer and dispatch date.
- **Courier deep-link tracking** — `CourierServicesTbl.TrackingUrlParam` (e.g. Fastway `?l=`, Pargo `?code=`, Courier Guy `?ref=`). Emails and Order Detail link the waybill number when a param is set. Go-live pack: `App_Data/GoLive/SQLCommands-CourierServices-01.xml` (and `App_Data/SQLCommands-CourierServices-01.xml`).

### Fixes
- **Send Reminder SQL** — `GetCustomerTypicalItems` no longer uses illegal `SELECT DISTINCT` + `ORDER BY` on a non-selected column.
- **Send Reminder templates** — Manual reminder no longer depends on `SendCheckupEmailTextsTbl` column/name mismatches; content comes from Messages.resx.
- **SendCheckEmailTexts repository** — Legacy Access table name corrected to `SendCheckupEmailTextsTbl` (for the batch Send Coffee Checkup page).
- **Order Detail waybill UI** — Removed cluttered inline editors and the separate “track” label; number is the hyperlink when a deep-link param exists.
- **HtmlEditor toolbar** — Site.css exclusions so AjaxControlToolkit editor chrome is not crushed by global button styles (cache bust on Site.Master).
